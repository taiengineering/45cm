## 1. 개발 범위

### 1차 개발: Knowledge Publishing Engine

법령·신뢰 DB 기반 질문·답변 생성 및 자동 웹 게시 엔진.

신뢰 원천 → 질문 생성 → 근거 결합 → 답변 생성 → 자동 검증 → 게시 승인 판정 → 웹 발행 → 사후 관측

이 엔진은 대량생산형이므로 사람 검수를 전제로 하지 않는다. 사람은 개별 콘텐츠를 검수하는 것이 아니라 다음을 관리한다: 원천 허용 정책, 생성 규칙, 검증 기준, 금지 기준, 표본 감사, 긴급 중지.

### 2차 개발: Channel Marketing Engine

채널별 콘텐츠 기획, 콘텐츠 생성, 채널별 변환, 이미지·영상·본문 생성, 게시 일정 결정, 자동 발행, 반응 수집, 성과 기반 다음 콘텐츠 추천.

LLM 선택 기준은 단순 모델 성능이 아니라 다음의 결합으로 판단한다: 품질 × 재생성률 × 콘텐츠당 비용 × 처리시간 × 채널 적합성

운영 모드: 기본 경로 = 완전 자동. 예외 경로 = Assisted. 특수 경로 = Manual. 사람이 매번 작성·복사·게시하는 방식은 구현 대상에서 제외한다.

### 3차 범위: Contact Data Acquisition Engine

이번 단계에서는 전체 구현하지 않고 다음만 설계한다: 객체 구조, 외부 데이터 소스 경계, 수집 계약, 이메일·휴대전화 표준 스키마, 출처 증거 구조, 검증 상태, 개인정보·접촉 가능 상태, 다른 엔진과의 연결 계약, 향후 확장 지점.

구조와 계약은 만들되 실제 수집기는 후속 개발로 둔다.

## 2. 개발 순서

기존 자산은 재사용하지 않는다.

```
전체 구조 설계
→ 공통 객체·계약 설계
→ 검증 레이어 설계
→ 1번 엔진 개발
→ 1번 엔진 운영 검증
→ 2번 엔진 개발
→ 1·2번 연결 검증
→ 3번 구조 등록
```

1번과 2번을 동시에 개발하지 않는다. 다만 2번 개발 때 다시 공통부를 만들지 않도록, 전체 구조와 공통 계약은 먼저 설계한다.

---

## 3. 기존 자산 처리

| 항목 | 처리 |
|---|---|
| 기존 저장소 | 보존 후 동결 |
| 기존 Runtime 40개 | 재사용하지 않음 |
| 기존 DB 90개 | 신규 시스템 SoT로 사용하지 않음 |
| 기존 Console | 재사용하지 않음 |
| 기존 API | 재사용하지 않음 |
| 기존 기획 문서 | 역사·참고자료로만 보존 |
| 기존 도메인 | 신규 시스템에서 사용하지 않음 |
| 기존 배포 구조 | 신규 설계의 제약조건으로 삼지 않음 |

이는 기존 코드 품질이 나빠서가 아니라, 기존 자산이 45CM 헌법 이전에 만들어졌고 객체·계약·DB 정본 원칙을 따르지 않았기 때문이다. 새 프로젝트에 기존 자산을 일부 섞으면 신규 구조 내부에 다시 직접 연결, 중복 데이터, 중앙 허브가 생길 가능성이 크다.
